## Issue Report

> The discount cap doesn't behave correctly. In some cases the discount amount returned
> is higher than the cap; in others a discount that should be below the cap gets capped
> anyway.

## Expected Behavior

`calculate_discount_amount` computes `raw = subtotal * percent / 100`, then returns
`min(raw, max_discount_amount)` — the cap limits the computed percentage, not the order total.

## Actual Behavior

The cap check compares `subtotal` against `max_discount_amount`. When `subtotal > cap`,
the cap is returned even if `raw < cap`. When `subtotal <= cap`, the cap is never applied
even if `raw > cap`.

## Root Cause Description

`discount_service.py` lines 27–28:
```python
# BUG
if discount.max_discount_amount is not None and subtotal > discount.max_discount_amount:
    return discount.max_discount_amount
# CORRECT
if discount.max_discount_amount is not None and raw > discount.max_discount_amount:
    return discount.max_discount_amount
```
`subtotal` (the order total) is used as the comparand instead of `raw` (the computed
discount amount). Example: subtotal=30, percent=50%, cap=20 → raw=15, but since 30>20
the function returns 20 (the cap), which is wrong because raw=15 is below the cap.

## Reproduction Steps

1. Create a discount: 50% with `max_discount_amount=20`.
2. Call `POST /discounts/apply` with `subtotal=30`.
3. Observe `discount_amount=20` instead of the correct `15`.
